Part I

The Problem

Why serving a model is a different engineering game from training it — and why the bill arrives per token.

SECTION 11.1

The Serving Equation — Throughput vs Latency

Training optimizes total throughput over weeks. Serving optimizes two numbers at once: latency (how fast one user's next token arrives) and throughput (how many tokens the whole GPU ships per second). One equation controls both, and it is memory-shaped, not compute-shaped.

🎯 By the end of this section, you will be able to predict how many times a model's weights are read during any response, and explain why decode is memory-bound — not compute-bound.

Autoregressive = Serial

A 100-token response is 100 sequential forward passes. You cannot parallelize them — token 47 does not exist until token 46 exists. This serial chain is the single biggest structural fact of serving, and it is why per-token latency dominates the user experience.

1 passper token, forever, no shortcuts at the algorithm level

Memory-Bound Decode

Generating one token means reading all the weights from HBM once: 14 GB for 7B fp16. At ~2 TB/s of GPU bandwidth that is ~7 ms of pure memory time — the FLOPs finish early and wait. This is why every trick in this module reduces bytes moved, not FLOPs.

14 GBread from memory per token · 7B fp16

Two Bosses, One GPU

Latency wants one user, now. Throughput wants many users, sustained. Batching (11.6) reconciles them: the same weight read can feed many tokens at once. The trick is never letting the GPU idle while any user waits.

2×goals — the whole module is a negotiation between them

🧮 Worked Example — One Token, One Full Read

Decode is a memory problem. A 7B model in fp16 stores its weights as 7 billion 2-byte numbers:

W_bytes = 7 × 10⁹ × 2 B = 14 GB

Every generated token needs every weight, so the GPU reads the whole crate from HBM. On an A100-class card with ~2 TB/s of bandwidth (approx):

t_token ≈ 14 GB ÷ 2 TB/s ≈ 7 ms  →  ≈ 140 tokens/s per stream

Now run the whole response. Two users, 100 tokens each, no batching yet:

weight reads = 2 × 100 = 200  →  200 × 14 GB = 2.8 TB of memory traffic

→ The weights are read once per token per user. Nothing is reused between users or between tokens — yet. The next four sections exist to change exactly this: reuse (11.2), shrink (11.4), skip (11.5), share (11.6).

$$t_{\text{token}} \approx \frac{W_{\text{bytes}}}{\text{BW}_{\text{HBM}}} \qquad \text{latency} \approx n_{\text{tokens}} \times t_{\text{token}} \qquad \text{throughput} \approx B \times \frac{1}{t_{\text{token}}}$$

Throughput is batching's payoff: if the GPU reads the weights once and applies them to B different tokens, throughput multiplies by B while per-user latency stays flat. That multiplication is the entire business of 11.6 — and it is why providers quote you tokens per second, not answers per second.

📦
Why "memory-bound" is the phrase to keep: an A100 can do ~312 teraFLOPs, but a 7B forward pass only needs ~2×7×10⁹×2 ≈ 28 gigaFLOPs per token — the arithmetic finishes in a fraction of a millisecond and then waits for memory. Servers are bought by bandwidth, not FLOPs. This one sentence explains why HBM bandwidth (not compute) appears on every GPU marketing slide.
🌊
Real serving numbers (approx): a frontier-class 400B model serves ~20–40 tokens/s per stream on 8×H100 — because it must stream ~800 GB of weights per token. A 7B model serves ~100–200 tok/s per stream. The "tokens/sec per GPU" race is a bytes-per-token race wearing a disguise.

200 times. Each generated token is a full forward pass, and a forward pass reads every weight. This brutal repetition is exactly what the KV cache (11.2) partially fixes and what batching (11.6) amortizes.
SECTION 11.2 ★ THE ESSENTIAL OPTIMIZATION

The KV Cache — Never Recompute the Past

Without a cache, generating token 100 recomputes attention for all 99 previous tokens. With one, every past token's keys and values are saved once, and each new token computes a single new row. This section runs the ledger, does the memory math, and reveals the cost: the cache grows with context, and that growth is the real price of long-context serving.

🎯 By the end of this section, you will be able to compute any model's cache memory from its spec card, and explain why the cache turns O(n²) decode into O(n) — while making long contexts memory-hungry.

🧮 Worked Example — Token 4, With and Without the Cache

Toy world: L = 2 layers, H = 2 heads, d_head = 2, and 4 tokens in context. Without a cache, generating token 4 recomputes every score in every head — all T×T cells per layer:

score cells, no cache = L × H × T² = 2 × 2 × 16 = 64

With a cache, token 4's query only needs to match against the 4 cached key rows — one new row of scores per head:

score cells, cached = L × H × T = 2 × 2 × 4 = 16

Now extend to a real decode run of n tokens. Token t costs t·(L·H) cells uncached, but only (L·H) cached:

total cells = L·H·Σt = L·H·n(n+1)/2  vs  L·H·n

→ Uncached attention is O(n²) in sequence length; cached decode is O(n). At n = 4,096 with L·H = 256 heads, that is ~2.1 billion score cells saved per response. The cache is not a speed hack — it is the difference between quadratic and linear decode.

$$M_{\text{cache}} = \underbrace{2}_{K,V} \times L \times H \times d_h \times T \times B \times \text{bytes}$$
L · layers H · heads d_h · head dim T · context tokens B · batch

Hover the chips to see each term light up in the ledger above. The 2 counts K and V. Everything except B and bytes is a fixed property of the model — so per sequence, the cache grows linearly with context length T. That linear growth is the entire story of long-context serving: the weights are a fixed crate, but the cache is a rope you pay for by the meter.

🗄️
PagedAttention (vLLM, 2023): naive serving allocates one contiguous block per request's maximum context — most requests use a fraction of it. PagedAttention manages the cache like virtual memory: 4KB-ish pages, allocated on demand, shared across prefix matches. It is the single biggest throughput win in modern serving — vLLM, TGI, and SGLang all use it.
📉
GQA and MLA (Llama-3, Mistral, DeepSeek): Grouped-Query Attention shares K/V across query heads — Llama-3-8B caches only 8 KV heads instead of 32, cutting cache bytes 4×. DeepSeek's Multi-head Latent Attention compresses the cache into a latent vector, cutting it by ~90%. Architecture is a cache-size decision now.
📓 Instruction Manual · How Big Is the Cache? The Memory Math, Page by Page

Page 1 · One Token, One Row, Everywhere

K1Each generated token must be remembered in every layer and every head — that is what "the past is never recomputed" means. The per-token cost is small and fixed:

$$M_{\text{per token}} = 2 \times L \times H_{KV} \times d_h \times \text{bytes}$$

Take a 7B-class dense model: L = 32 layers, H = 32 heads (no GQA), d_h = 128, fp16 (2 bytes):

$$2 \times 32 \times 32 \times 128 \times 2 = 524{,}288 \text{ B} = 512 \text{ KiB per token}$$

One token costs half a megabyte of cache. Harmless — until you count the tokens.

Page 2 · Context 4,096 → The GB Arrives

Multiply by the context length — every prompt token and every generated token occupies its row:

$$512 \text{ KiB} \times 4{,}096 = 2 \text{ GiB per sequence}$$

So serving a 7B model (14 GB of weights) at 4K context pays a 2 GB cache per concurrent user. Sixteen users at 4K: 32 GB of cache — more than the weights. This is why VRAM math for serving always says "weights + cache × users", never just "weights".

The same model at 128K context: 512 KiB × 131,072 = 64 GiB per sequence. That number is why long-context models need GQA, quantization, paged caching — or fewer concurrent users. Long context is a memory tax, and the cache is the tax collector.

Page 3 · Reading the Spec Card Like an Operator

The operator's habit: cache bytes per token = 2 × L × H_KV × d_h × bytes. Check it against real models (approx):

$$\text{Llama-3-8B (32L, 8 KV heads, fp16): } 2\times32\times8\times128\times2 = 128 \text{ KiB/token}$$

128 KiB × 8,192 context = 1 GiB per sequence — 4× smaller than the 7B-MHA case above, purely from GQA. The formula on this page is the one to quote in a capacity review: it turns "will it fit?" into arithmetic you can do on a napkin. It also explains the exam incident in Part V about an OOM at long context — the cache, not the weights, is what overflowed.

Cache is free at generation time only if you paid for it at allocation time. Every serving framework shows you "KV cache utilization" for exactly this reason — it is the meter that tells you how close you are to OOM.

🔮 Predict Before You Compute
A model's KV cache is allocated per sequence. As a conversation's context length grows from 1,000 to 8,000 tokens, what happens to the cache's memory footprint?
It grows 8× — linearly. Each token appends 2 × L × H × d_h numbers, so memory is proportional to tokens (T), not T². The quadratic term in attention is compute — and the cache is precisely the trick that converts that quadratic decode compute into linear memory. The price of the fix is that the cache itself grows with context: 8,000 tokens cost 8× the cache of 1,000.
Part II

The Machines

Two machines that change where the numbers live: FlashAttention stops the quadratic matrix from existing, and quantization shrinks the crate itself.

SECTION 11.3

FlashAttention — The Matrix That Never Exists

Naive attention materializes the full N×N scores matrix in slow HBM — at N = 128K that is 16 billion floats per head per layer. FlashAttention processes attention in tiles, keeping only a running max and running sum (the stable-softmax trick from Module 04), so the full matrix is never written to memory. Same math, same output, 10–20× less memory, 2–4× faster.

🎯 By the end of this section, you will be able to compute the memory savings of tiling for any N, and reproduce the online-softmax rescale — the two-line trick that makes the whole thing exact.

🧮 Worked Example — Online Softmax, the Two-Pass Secret (real numbers)

Attention must softmax each score row. FlashAttention sees the row only in tiles, so it keeps a running max m and a running sum ℓ, rescaling when a bigger score arrives. Watch tile 1 of the row z = [3.0, 1.0]:

z₁ = 3.0: m = 3.0, ℓ = e^(3−3) = 1  ·  z₂ = 1.0: m stays 3.0, ℓ = 1 + e^(1−3) = 1.1353

No rescale needed yet — m never moved. The whole tile's contribution is summarized by the pair (m, ℓ) = (3.0, 1.1353).

Tile 2 arrives with z = [0.5, −2.0] — no new maximum, so the pair simply joins the running sum:

ℓ = 1.1353 + e^(0.5−3) + e^(−2−3) = 1.1353 + 0.0821 + 0.0067 = 1.2241

Then tile 3 opens with z₃ = 5.0, and the new max beats the old one — this is the moment that makes FlashAttention exact:

z₃ = 5.0: m_old = 3.0 → m_new = 5.0  →  ℓ = 1.2241·e^(3−5) + e^(5−5) = 1.2241·0.1353 + 1 = 1.1656

Every old exponential is rescaled by e^(m_old − m_new) = e^(−2) in one multiply — because e^(z−5) = e^(z−3)·e^(−2). The rest of the tile joins the sum the same way.

At the end, divide by the final ℓ — identical to the naive full softmax:

p = e^(z−5) ÷ 1.1656 = [0.1353, 0.0183, 0.0111, 0.0009, 1] ÷ 1.1656 = [0.116, 0.016, 0.010, 0.001, 0.858]

→ FlashAttention's output equals naive attention to floating-point precision, but it only ever held 5 exponentials and 2 scalars in fast memory — never the 16 elements of the row, and certainly never the N×N matrix. The lab below animates exactly this ledger, tile by tile.

📓 Instruction Manual · Why the Rescale Is Exact — Online Softmax, Derived

Page 1 · The Identity That Makes It Work

F1Softmax is shift-invariant: subtracting any constant c from every score changes nothing, because the c cancels in the ratio:

$$\frac{e^{z_i - c}}{\sum_j e^{z_j - c}} = \frac{e^{z_i} e^{-c}}{e^{-c} \sum_j e^{z_j}} = \frac{e^{z_i}}{\sum_j e^{z_j}}$$

FlashAttention exploits the same identity dynamically: when a new tile brings a larger maximum m_new, the old exponentials are still valid — they just need shifting by the difference. One multiply per old term:

$$e^{z_i - m_{\text{new}}} = e^{z_i - m_{\text{old}}} \cdot e^{m_{\text{old}} - m_{\text{new}}}$$

Page 2 · The Ledger, Worked by Hand

Take z = [3.0, 1.0, 0.5, −2.0, 5.0] with tile size 2. Tile 1: z₁ = 3.0 sets m = 3.0, ℓ = 1; z₂ = 1.0 joins: ℓ = 1 + e^(−2) = 1.1353. Tile 2: z₃ = 0.5, z₄ = −2.0 — no new max, ℓ = 1.1353 + e^(−2.5) + e^(−5) = 1.2241. Then the bomb, tile 3:

$$z_5 = 5.0:\quad \ell = 1.2241 \cdot e^{3-5} + 1 = 1.2241 \cdot 0.1353 + 1 = 1.1656$$

Old contributions shrank by e^(−2) in one step; the new element contributes e⁰ = 1. Final probabilities: e^(z−5) ÷ 1.1656 = [0.116, 0.016, 0.010, 0.001, 0.858] — check against the naive formula: identical.

The value of m only ever increases. Each increase triggers exactly one rescale multiply of the running sum — O(1) work per new maximum, no matter how many tiles came before.

Page 3 · From Scores to Output — the Weighted Blend

Softmax probabilities are not the output; the output is Σ pᵢ·vᵢ. FlashAttention tracks a third running quantity, the accumulated output o, rescaled with the same factor whenever m moves:

$$o \leftarrow o \cdot e^{m_{\text{old}} - m_{\text{new}}} + p_{\text{new}} \cdot v_{\text{new}}$$

At the end: output = o ÷ ℓ. Three running values (m, ℓ, o) and one tile — that is the entire FlashAttention forward pass. The backward pass recomputes the tiles (the "recompute" trick) to avoid storing them, trading a little compute for a lot of memory. Module 04's stable-softmax notebook is this exact identity; this is its production form.

"Exact" in the paper's title means: bit-identical (up to float rounding) to naive attention. No approximation, no pruning — just a different address space for the same arithmetic.

What exactly does FlashAttention avoid materializing in memory?
The full N×N scores matrix. The QKᵀ product is the only N² object in attention, and at 128K context it would be 32 GB per head per layer in fp16. SECTION 11.4

Quantization — Fewer Bits, Same Brain

A 7B model in fp16 needs 14 GB. In int8: 7 GB. In int4: 3.5 GB — small enough for a laptop, a phone, or 4× more users per GPU. The catch is rounding error: every weight is snapped to the nearest representable value. This lab quantizes a real weight distribution and shows, honestly, what breaks and what survives.

🎯 By the end of this section, you will be able to compute the rounding error of any bit-width from first principles, and explain why 4-bit models work at all — and when they visibly don't.

$$\Delta = \frac{x_{\max} - x_{\min}}{2^b - 1} \qquad \text{max err} = \frac{\Delta}{2} \qquad \text{RMS err} \approx \frac{\Delta}{\sqrt{12}}$$

Hover the chips to highlight the step grid and the error band in the histogram above. The RMS-error formula is the classic result for uniform rounding: errors are uniformly spread within ±Δ/2, and a uniform distribution's standard deviation is Δ/√12 ≈ 0.289Δ. Each bit removed doubles the step — the 8→4 drop is a ~17× error increase, which is why it is a real event, not a cosmetic one.

🗜️
The real formats (2024–2026): GPTQ and AWQ quantize weights for GPU inference — AWQ explicitly protects the ~1% of "salient" weights that matter most, keeping them at higher precision. GGUF (llama.cpp) is the CPU/edge standard; Q4_K_M is the famous 4-bit sweet spot. FP8 goes further: DeepSeek-V3 trained in FP8 mixed precision, halving memory during training itself.
⚖️
The honest tradeoff: 4-bit weight-only quantization costs ~1–3% on hard benchmarks but runs 3–4× faster and fits in a fraction of the memory. Below 4 bits the cliff is real: 2-bit and 1.58-bit ternary are active research, not production defaults. And on sensitive tasks — long arithmetic chains, precise formatting — the 1–3% can land right where you can't afford it. That asymmetry is exam scenario 3.
📓 Instruction Manual · The Error Math of Quantization

Page 1 · The Step Size, Worked

Q1Weights in a real model roughly live in [−2, 2] (LayerNorm keeps activations tame; weights follow). Uniform quantization divides that range into 2^b levels:

$$\Delta = \frac{4}{2^b - 1} \qquad b=4:\ \Delta = 0.267 \quad b=8:\ \Delta = 0.0157 \quad b=16:\ \Delta = 0.00006$$

Each weight snaps to the nearest level; the worst case loses Δ/2. At 4 bits, max error 0.13 — compared to a typical weight magnitude of ~0.2–1.0, that is a 10–60% relative error on individual weights. And yet 4-bit models work. Page 2 is why.

Page 2 · Why It Works at All — Errors Average Out

Quantization error is roughly symmetric noise: as many weights round up as down, with RMS ≈ Δ/√12. A forward pass sums thousands of these errors per neuron:

$$\text{RMS err} = \frac{\Delta}{\sqrt{12}} \qquad b=4:\ 0.077 \quad b=8:\ 0.0045 \quad b=16:\ 0.000018$$

Independent-ish errors partially cancel in the sums — the model behaves like a network with slightly noisy weights, and trained networks are famously robust to small weight noise. Two refinements make 4-bit practical: per-group scales (each small group of weights gets its own Δ, so outliers don't stretch everyone's grid) and outlier preservation (AWQ keeps the ~1% of weights whose magnitude matters most at higher precision).

The lab's "model quality" proxy is deliberately a proxy: it models quality as 100 − 25×RMS — honest about being a stand-in, calibrated so 4-bit shows a small visible dip and 2-bit collapses, which is what real evals show.

Page 3 · The Memory Arithmetic

The crate shrinks linearly with bit-width. A 7B model:

$$\text{fp16: } 7\times10^9 \times 2 = 14 \text{ GB} \qquad \text{int8: } 7 \text{ GB} \qquad \text{int4: } 3.5 \text{ GB}$$

And the serving math compounds: 4-bit weights mean 4× fewer bytes per token read, so decode gets ~4× faster even before you count the extra users that fit in VRAM. Quantization is the only optimization in this module that attacks all three terms — memory, bandwidth, and cost — at once. That is why it is the default first move in every production deployment.

Rule of thumb from production: quantize the weights, keep the cache in fp16. The cache stores activations that flow through softmaxes — it tolerates noise far worse than weights do, and modern engines (vLLM, TensorRT-LLM) do exactly this split.

4-bit quantization snaps every weight to one of 16 levels — up to 10× coarser than the original values. Why does the model still work?
Errors average out. Quantization error is symmetric (RMS ≈ Δ/√12), each neuron sums thousands of weights, and independent errors partially cancel — the network behaves like one with slightly noisy weights, which trained networks tolerate. Part III

The Speed

Two ways to make the GPU ship more tokens per second: guess more tokens per pass, and share each pass across more users.

SECTION 11.5

Speculative Decoding — Guess, Then Verify

Decode is serial: one token per big-model pass. Speculative decoding breaks the serial chain with a small, fast draft model that proposes K tokens, then the big model verifies all K in one parallel pass. Accepted tokens are free. The expected number of accepted tokens has a closed form — and this section derives it, animates it, and finds where it fails.

🎯 By the end of this section, you will be able to derive the expected-acceptance formula E[k] = (1 − α^k)/(1 − α), predict the speedup for any acceptance rate, and state when speculation loses.

🧮 Worked Example — Four Drafts, One Verify, Real Counts

α = 0.7, K = 4. The draft proposes 4 tokens; the big model checks them in one parallel pass. Acceptance is a geometric-like cascade: token 1 accepted with prob α, token 2 given token 1 with prob α, and so on — and the first rejection stops the run. Count the tokens each round produces:

P(1 token) = 0.3 (first draft rejected — the big model still emits one)  ·  P(2 tokens) = 0.7·0.3 = 0.21  ·  P(3 tokens) = 0.7²·0.3 = 0.147

P(4 tokens) = 0.7³·0.3 + 0.7⁴ = 0.1029 + 0.2401 = 0.343. Expected tokens per verify round:

E = 1·0.3 + 2·0.21 + 3·0.147 + 4·0.343 = 2.53

Now the cost. The draft model costs c ≈ 15% of a big-model pass per token (toy: it is tiny); the big model costs 1 pass per verify round regardless of K:

cost per round = K·c + 1 = 4×0.15 + 1 = 1.6  →  speedup = E ÷ 1.6 = 2.53 ÷ 1.6 ≈ 1.58×

→ At α = 0.7 the stack is 58% faster. Crank α to 0.9: E = 3.44, speedup = 2.15×. Real deployments report 2–3× — the draft model (a small sibling, or Medusa heads on the same model) is trained to match the big model's distribution, pushing α up to 0.7–0.9.

As α → 0, E[k] → 1 — you pay the draft's cost for zero benefit. The curve's shape is why speculation is a distribution-matching problem: the entire engineering is making the small model think like the big one.

🐍
Medusa (2024) and EAGLE: instead of hosting a second model, add tiny "Medusa heads" to the big model that propose the next several tokens in parallel — self-speculative decoding. Same verify logic, no second model to serve. This is where the field converged: the draft lives inside the big model.
🛑
When speculation loses (exam scenario 4): if acceptance is low (α ≲ 0.4), the draft cost eats the win — decode is break-even at best, and slower than greedy once real overhead lands. Speculation also stops paying when the GPU is already saturated — under heavy batching there is no spare bandwidth for a "free" parallel verify pass. Always measure, never assume.
📓 Instruction Manual · Deriving E[k] — the Expected-Acceptance Formula

Page 1 · The Cascade of Probabilities

S1Each draft token is accepted independently with probability α — until the first rejection, which ends the round. Count what the round produces: if the first draft is rejected, the big model still emits one token; k accepted drafts followed by a rejection produce k+1 tokens; all K accepted produce K. The cascade:

$$P(\text{produce } k+1 \text{ tokens}) = \alpha^k (1-\alpha) \quad (k = 0 \dots K-1), \qquad P(\text{produce } K) = \alpha^K$$

Check with α = 0.7, K = 4: P(1) = 0.3, P(2) = 0.21, P(3) = 0.147, P(4) = 0.1029 + 0.2401 = 0.343 — and the probabilities sum to 1 (0.3 + 0.21 + 0.147 + 0.1029 + 0.2401 = 1). The cascade is a truncated geometric distribution, and its mean has a beautiful closed form.

Page 2 · The Closed Form

The expected number of tokens per round: slot j is filled iff every earlier draft was accepted — probability α^j. Sum over j = 0…K−1 and the finite geometric series closes in one line:

$$E[\text{tokens per round}] = \sum_{j=0}^{K-1} \alpha^j = \frac{1 - \alpha^K}{1 - \alpha}$$

Work the numbers for α = 0.7, K = 4: (1 − 0.7⁴)/(1 − 0.7) = (1 − 0.2401)/0.3 = 2.533. The lab's live readout computes this exact number — and the animated loop above measures it empirically, round after round.

The same formula appears in queueing theory as the mean of a truncated geometric series. "Expected accepted tokens" is just a fancy name for a truncated geometric mean.

Page 3 · From Tokens to Speedup

Tokens are not free: the draft costs c per token, the big model costs 1 per round. Per round, expected tokens = E, expected cost = K·c + 1:

$$\text{speedup} = \frac{\text{tokens per round with spec}}{\text{cost per round with spec}} \div \frac{1 \text{ token}}{1 \text{ pass}} = \frac{E}{K c + 1}$$

Numbers: α = 0.7, K = 4, c = 0.15 → 2.533/1.6 = 1.58×. α = 0.9 → 3.44/1.6 = 2.15×. And the failure mode falls out of the same formula: α = 0.4 → E = 1.62, speedup ≈ 1.02× — break-even at best, and slower than greedy once the draft's real overhead lands. The formula doesn't have an opinion; it just bills you for the draft.

Sampling detail that matters in production: when a draft token is rejected, the big model's own token for that position is used instead — so speculative decoding with sampling is distribution-preserving, not just "sometimes right". The 2–3× speedup comes with zero change to the output distribution.

🔮 Predict Before You Compute
A team deploys speculative decoding with a draft model that only agrees with the big model 40% of the time (α = 0.4, K = 4, draft cost 15%). What happens to decode speed?
It gets slower — the win is gone. Speculation is a bet on the draft. With α = 0.4 the 0.6 passes of draft cost per round buy only 1.62 tokens — the arithmetic (E ÷ (K·c + 1)) lands at ≈1.02×: break-even at best, and real overheads push decode below 1×. The failure is invisible in a demo with a good draft; it only shows in production telemetry. Rule: measure the acceptance rate in production, and disable speculation below ~0.6 or when the GPU is saturated.
SECTION 11.6

Batching — One Weight Read, Many Tokens

Decode is memory-bound: the GPU reads 14 GB of weights per token. But a single read can feed many tokens at once if they all share the pass. Naive batching waits for the whole batch to finish; continuous batching swaps finished sequences out mid-generation. This lab runs both schedulers side by side and meters the difference.

The magic of batching: per-user latency is unchanged (each user's tokens still arrive one per pass), but the GPU's weight read is shared across B users — so total tokens/sec multiplies by B. Utilization is the honest meter: every empty slot is bandwidth spent once and used zero times.

🧩
Continuous batching (vLLM, 2023; TGI; SGLang): static batching suffers the "straggler" — a 20-token response holds the whole batch while 8-token responses sit done. Continuous batching evicts finished sequences immediately and admits new ones into the freed slots, keeping the GPU full. Measured result: 2–5× throughput at scale, with no latency change for users.
⚙️
Disaggregated serving (2024+): prefill (long prompt, compute-heavy) and decode (short context, memory-bound) have opposite bottlenecks, so production stacks split them onto different GPU pools. Prefill nodes chew the prompt; decode nodes stream the answer. Same batch math, two different machines.
🔮 Predict Before You Compute
Why does batching multiply tokens/sec on a memory-bound GPU without slowing any single user down?
One weight read serves B tokens. Decode's bottleneck is memory traffic, not arithmetic: the GPU streams the weights once per pass, and a pass can carry B tokens' computations. Sharing the read is free — the FLOPs were idle anyway. The catch is memory: B users need B× the KV cache, so batch size is ultimately a VRAM budget decision (you will feel this in the 11.7 builder).

You serve a 7B fp16 model (14 GB weights) at 4K context, batch 16. Which component most determines how much VRAM you must provision?
The cache. Weights are a fixed 14 GB; the cache is 2 GB per concurrent sequence at 4K context (from the 11.2 notebook). At batch 16 the cache is 32 GB — 2.3× the weights. This is why real serving clusters watch "KV cache utilization" like a fuel gauge, and why GQA and paged attention are the difference between fitting and not fitting. 💸

The gap is not markup — it is the bytes-per-token of a 400B model vs a 7B model. When a provider says "priced by token", they are pricing memory traffic with a currency.
📉
The macro trend: the cost of equivalent capability has fallen roughly 10× per year since GPT-3 — hardware (H100→B200), quantization (fp16→FP8→int4), serving software (vLLM, continuous batching), and architecture (GQA, MoE, MLA) all push the same curve down. Design for the cost curve: a feature too expensive today is cheap in a year.
🔮 Predict Before You Compute
Why do LLM providers meter by token rather than by question or by conversation?
Cost is proportional to tokens. Each generated token is a full weight read plus a growing cache read — a predictable, measurable amount of memory traffic. A 50-token answer costs ~50/140 of a GPU-second on a 7B; a 2,000-token answer costs 40× more. Questions and conversations have no such linear relationship to machine work — tokens do. Token metering is the price of physics wearing a billing label.
